## Нагрузочное тестирование REST-сервиса калькулятора с использованием Apache JMeter

---

## Цель работы

Целью является ознакомление с возможностями нагрузочного тестирования веб-приложений с использованием инструмента Apache JMeter, а также анализ поведения приложения при различной интенсивности нагрузки.

В рамках работы проводилось тестирование REST-сервиса.

---

## Тестируемое приложение

Тестируется REST-эндпоинт:

### POST /api/calc

Сервис принимает JSON-запрос вида:

```json
{
    "a": 10,
    "b": 5,
    "operation": "add"
}
```

и возвращает:

- HTTP 200 — при корректной операции
- HTTP 422 — при ошибке валидации (например, деление на ноль)

## Описание входных данных

### 1. jmeter/data/calc_ok.csv

Файл содержит корректные JSON-запросы для выполнения операций калькулятора.

Каждая строка файла — это тело POST-запроса, например:

```json
{ "a": 10, "b": 5, "operation": "add" }
```

Назначение:

- генерация успешных запросов
- проверка стабильности сервиса при валидных операциях
- ожидаемый HTTP-код: 200

### 2. jmeter/data/calc_div0.csv

Файл содержит JSON-запросы с делением на ноль.

Пример строки:

```json
{ "a": 10, "b": 0, "operation": "div" }
```

Назначение:

- генерация ошибочных запросов (деление на ноль)
- проверка корректности обработки ошибок сервисом
- ожидаемый HTTP-код: 422

## Описание тестового плана (lab4-calculator.jmx)

Тестовый план включает следующие элементы:

### 1. HTTP Request Defaults

- Host: localhost
- Port: 8080
- Protocol: http
- Implementation: HttpClient4

Позволяет централизованно задать параметры подключения.

### 2. HTTP Header Manager

Добавлен заголовок:

```json
Content-Type: application/json
```

Обеспечивает корректную передачу JSON-тела запроса.

### 3. HTTP Cookie Manager

Используется для управления cookie при тестировании.

### 4. Thread Group

Основные параметры:

- Number of Threads (users): от 1 до 10000
- Ramp-up period: 20 секунд
- Loop Count: 10

Это означает, что:

- указанное количество виртуальных пользователей
- постепенно запускаются в течение 20 секунд
- каждый выполняет 10 итераций

### 5. Transaction Controller

Используются два транзакционных контроллера:

**TX-calc-ok**

- Тестирование корректных операций
- Включает:
    - CSV Data Set Config (calc_ok.csv)
    - POST /api/calc
    - Response Assertion (ожидается 200)

**TX-calc-div0**

- Тестирование деления на ноль
- Включает:
    - CSV Data Set Config (calc_div0.csv)
    - POST /api/calc
    - Response Assertion (ожидается 422)

## Инструменты анализа

В тестовый план добавлены:

- Summary Report
- Aggregate Report
- View Results Tree

### Summary Report

Позволяет анализировать:

- количество запросов (# Samples)
- среднее время ответа (Average)
- минимальное и максимальное время
- процент ошибок (Error %)
- пропускную способность (Throughput)

### Aggregate Report

Дополнительно отображает:

- медиану (Median)
- 90%, 95%, 99% перцентили
- стандартное отклонение

Используется для анализа распределения задержек.

## Результаты тестирования

### 1 пользователь

- Среднее время ответа: 2–3 мс
- Ошибки: отсутствуют (кроме ожидаемых 422)
- Приложение работает стабильно

Вывод: сервис функционирует корректно при минимальной нагрузке.

### 100–500 пользователей

Наблюдения:

- Среднее время ответа остается в пределах 1–5 мс
- Throughput увеличивается пропорционально нагрузке
- Ошибок 5xx не наблюдается
- Приложение масштабируется линейно

Вывод: сервис стабилен при нагрузке в несколько сотен пользователей.

### 10000 пользователей

Наблюдения:

- Среднее время ответа ~600–700 мс
- 95-й перцентиль превышает 2000 мс
- Максимальное время ответа достигает нескольких секунд
- Появляются ошибки даже на корректных запросах (HTTP 200)
- Error % по TX-calc-ok ≈ 3–4%

Вывод:

При нагрузке 10000 одновременных пользователей наблюдается деградация производительности:

- рост задержек
- увеличение процента ошибок
- перегрузка сервера

## Определение предельной нагрузки

Максимальной нагрузкой, при которой приложение работает стабильно, можно считать диапазон до нескольких тысяч одновременных пользователей.

После превышения этого значения:

- резко увеличивается latency
- появляются реальные ошибки обработки
- нарушается SLA по времени ответа

Таким образом, предельная нагрузка находится ниже 10000 пользователей.

## Общие выводы

Apache JMeter позволяет эффективно моделировать нагрузку на REST-сервис.

- При нагрузке до нескольких сотен пользователей приложение демонстрирует:
    - линейный рост throughput
    - стабильное время ответа
    - отсутствие критических ошибок
- При экстремальной нагрузке (10000 пользователей):
    - происходит рост задержек
    - появляются ошибки
    - сервис достигает предела производительности

Работа подтверждает необходимость нагрузочного тестирования для определения масштабируемости и устойчивости системы.
